1. 项目概览

桐乡市凤鸣高级中学工作台 是一个专为高一二班设计的全栈式班级管理应用。系统采用前后端分离架构，旨在实现班级信息透明化、管理高效化。包含学生端、教师端、班主任端（权限继承）以及管理员端，实现了通知下发、成绩录入与查询、课表管理、处分记录及批量数据导入等功能。

项目特点： 移动端适配、毛玻璃拟态UI、防截图水印、实时多端同步、无服务器架构（Serverless）。

2. 技术栈架构

Vue 3 (前端框架)

负责页面的渲染和交互。采用 Vue 3 的 Composition API 进行状态管理，实现数据驱动视图。通过 ref 和 reactive 管理页面状态和表单数据。

Tailwind CSS (样式框架)

负责全站UI设计。通过原子化 CSS 类名实现响应式布局（手机竖屏/电脑横屏）、玻璃拟态效果、阴影和动画过渡。

Supabase (后端即服务)

提供云端 PostgreSQL 数据库、Auth 身份认证、RLS（行级安全策略）。前端通过官方 SDK 直接操作云端数据。

SheetJS (xlsx)

用于在浏览器端解析 Excel/CSV 文件。实现学生名册批量导入和考试成绩批量导入的功能。

Vercel / Netlify (部署)

负责将静态代码托管到云端，提供 HTTPS 访问和自动 CI/CD 流程，无需服务器运维。

4. 页面结构详解

4.1 登录界面 (Login.vue)

采用左右分栏设计。左侧展示校训和背景装饰字“凤鸣”，右侧为毛玻璃拟态的登录卡片。

  • 顶部固定 Glassmorphism 导航条：显示“桐乡市凤鸣高级中学”。
  • 核心表单：输入账号和密码，点击“登录”触发 handleLogin 函数。
  • 底部提供“立即注册”和“管理员登录”的入口。

4.2 学生端 (dashboard)

  • 总览 (overview)：蓝色渐变个人信息卡片（含防截图水印），右侧展示安全设置（修改密码）。
  • 我的课表 (schedule)：手机端列表展示；电脑端为周一到周日的 7 列网格布局。
  • 成绩分析 (grades)：卡片式布局展示考试列表，点击可展开查看具体各科分数。
  • 通知中心 (notices)：列表展示通知，点击卡片无操作。
  • 个人处分 (punishments)：按级别区分颜色（红色-学校处分，橙色-班级处分），展示原因、处罚措施和作出机构。

4.3 教师端 / 班主任端 (teacher-dashboard)

  • 工作台 (overview)：教师欢迎卡片。
  • 发布通知 (publish)：输入标题和内容，支持删除已发布的通知。
  • 班级处分 (punish)：选择学生，录入处分原因，选择处罚措施（抬水、倒垃圾、自定义）。支持删除记录。
  • 班级名册 (students)：展示全班学生。支持 Excel 批量导入。若当前角色为班主任或管理员，每个学生旁会出现“编辑”按钮，可修改学号、姓名、职位和电话。
  • 成绩管理 (scores)：先创建考试（可多选科目），再进入成绩录入页。支持 Excel 导入和手动输入。

4.4 管理端 (admin-dashboard)

  • 概览 (overview)：显示总人数和通知数量。
  • 教师审核 (approvals)：查看待审核的教师和班主任，点击通过或拒绝。此操作会改变 profiles 表里的 status。
  • 处分管理 (punish)：有权限录入“学校处分”（可选机构：高一年级部、高二、高三）。可查看和删除所有处分记录。
  • 人员管理 (users)：查看全校所有注册用户。
  • 全局通知 (notices)：发布全校范围内的通知。

5. 数据库设计与 RLS 安全策略

项目使用 Supabase PostgreSQL 数据库。核心表包括：

  • profiles：用户资料表（id, student_id, name, role, status, class_name, phone）。
  • notices：通知表（tag, title, content, date）。
  • schedule：课表表（day, course, teacher）。
  • exams：考试表（name, date, subjects[], scores jsonb）。
  • punishments：处分表（student_id, student_name, reason, penalty, date, level, issuer）。

5.1 什么是 RLS？

RLS（Row Level Security）是 PostgreSQL 的安全机制。前端代码中暴露的 SUPABASE_ANON_KEY 是公开的，如果没有 RLS，任何人拿到这个 Key 都可以清空你的数据库。因此我们必须通过 RLS 规定：

  • 只有登录用户（TO authenticated）才能读取数据。
  • 学生只能查看数据，教师和班主任可以插入和删除通知、处分等数据。
  • 班主任和教师只有权更新 role='学生' 的个人的资料（通过 USING 子句限制条件）。

6. 核心业务逻辑与踩坑记录

⚠️ 处分显示逻辑的Bug（已修复）：
在处分录入时，下拉框获取的是数据库的 UUID，但学生端是用学号匹配的。由于类型不匹配，学生端一直显示空白。
解决方案： 在 addTeacherPunishment 和 addPunishment 函数中，先通过 allUsers.find(u => u.id === studentId) 查找真实的学号，写入数据库。同时，使用 computed 计算属性 myPunishments 进行双重匹配（匹配学号或UUID），确保数据100%显示。
💡 关于班级名册编辑权限：
由于前端角色继承，只要教师/班主任角色满足条件，即可看到“编辑”按钮。后端 RLS 策略通过 WHERE role='班主任' 和 WHERE role='学生' 双重限制，确保班主任只能编辑学生资料，不能修改其他教师的资料。
